# CanvasTTY Environments

> **Статус: предварительная версия.** Плагину нужен plugin API v2 CanvasTTY (сервисы плагинов, участие в запуске, окружения сессий, решающие хуки, инструменты плагинов и действия на карточках). Эти точки расширения предложены в основной проект и ещё не вошли в выпущенную версию, поэтому на текущем выпуске установка не пройдёт проверку манифеста.

Плагин CanvasTTY (manifest apiVersion 2): решает, **где работает окно** (worktree, сервер, контейнер), и забирает работу домой.
[English](README.md).

| Модуль | Что делает |
|:--|:--|
| `worktree` | **Где запустить → Git worktree**: окно работает в своём `git worktree` (новая ветка `canvastty/<окно>` или заданная) в папке данных плагина. Папка проекта не меняется. При закрытии окно спрашивает «Сохранить данные среды?»; *Remove* удаляет worktree и созданную ветку. |
| `ssh-host` | **Где запустить → SSH server**: окно работает на сервере из страницы **Настройки** плагина (метка, ssh-алиас или хост, пользователь, порт и какая локальная папка соответствует какой папке на сервере). Запуск превращается в `ssh -tt <host> 'cd <папка на сервере> && exec <shell или агент>'`; терминал, scrollback и статус остаются у CanvasTTY. Перед запуском и при восстановлении плагин за 8 с проверяет, что сервер отвечает и папка есть; иначе окно остаётся остановленным с причиной и никогда не запускается локально. На сервере ничего не устанавливается и не удаляется. |
| `container` | **Где запустить → Container**: окно работает в контейнере Docker или Podman на этом компьютере (сначала Docker, потом Podman; используется только уже запущенный движок). Образ берётся из **Настроек** (или поля *Image* в запуске), должен уже быть на компьютере (он никогда не скачивается) и содержать `python3`. `/workspace` — собственная копия (git worktree в папке данных плагина, забирается через *Collect changes*) или, если выбрать, сама папка проекта. Сети нет, если не отмечено *Allow network*; корень только для чтения, без capabilities, `no-new-privileges`, лимиты CPU/памяти/процессов, `/tmp` с `noexec`, одно нерекурсивное монтирование. Созданное движком сверяется с этим рецептом, а фиксированный Python-загрузчик проверяет то же изнутри до запуска чего-либо. Каждый запуск окна — `docker exec -it`; восстановление перезапускает тот же контейнер; закрытие удаляет его (и копию, если данные не сохраняются). |
| `remote-container` | **Где запустить → Container on a server**: тот же контейнер на сервере из **Настроек** (серверы `ssh-host`; по умолчанию Podman), в копии сопоставленной папки (git worktree рядом с ней, в `.canvastty-work/`) или в самой папке. Каждый шаг — один вызов ssh; shell окна — `ssh -tt <сервер> 'podman exec -it …'`. С этого компьютера в контейнер ничего не передаётся (ни переменные, ни ключи). |
| `results` | **Collect changes** в меню окон в worktree, на серверах и в контейнерах и инструмент оркестратора `canvastty-environments__collect`: работа окна становится новой локальной веткой `canvastty/<id8>-<название>` в вашем репозитории (с сервера — как `git bundle` по ssh). Файлы с секретами (`.env`, ключи, `.npmrc`, …) не забираются; ничего не сливается; текущая ветка и рабочая копия не трогаются; на сервере не остаётся ничего, кроме объектов самого репозитория. **Проверки в капсуле** (окна в worktree и контейнерах; инструмент `canvastty-environments__capsule`): *Run checks in a capsule* делает снимок рабочей копии окна (без файлов с секретами; ref `refs/canvastty/capsules/<id>` хранит его), распаковывает его в новый контейнер без сети и один раз запускает команду проверки из **Настроек**; уведомление и значок окна показывают успех/провал и последние строки. *Show check result* показывает результат снова; *Apply checked snapshot* превращает успешный снимок в новую ветку `canvastty/<id8>-<название>-checked`. |

## Установка

В CanvasTTY: **Расширения → Установить из GitHub**, вставьте URL репозитория, выберите модули, установите.
Пакет готов к установке как есть: сервисы — собранные однофайловые скрипты (`services/*.mjs`), в manifest указаны
размер и SHA-256 каждого файла.

## Подтверждения доверия

- Установка только копирует файлы. Сервисы запускаются после подтверждения **Extension native code** для плагина в
  **Настройки → Агенты** (код работает от вашего имени, как любая программа). Обновление или смена модулей отзывают
  подтверждение.
- `ssh-host` хранит в хранилище плагина только имена хостов, пользователей, порты и пути. Никаких паролей и ключей:
  ssh использует ваш `~/.ssh/config` и агент.
- Разрешения при установке: `storage` (страница настроек: серверы и настройки контейнеров), `environment:provide`
  (worktree, ssh-host, container, remote-container), `tools:agents`, `cards:decorate`, `sessions:events` (results;
  события — только метаданные окон, без текста экрана).
- `container`, `remote-container` и проверки в капсуле запускают CLI Docker/Podman от вашего имени, с собственной
  пустой папкой настроек Docker (без помощников учётных данных и контекстов из `~/.docker`). Они никогда не скачивают
  образы и не запускают Docker Desktop или машину Podman.

## Ограничения первой версии

- Агент на сервере запускается тем же CLI по имени из login shell сервера, без локальных мостов CanvasTTY (хуки
  статуса, браузер, инструменты оркестрации): аргументы, указывающие на файлы этого компьютера, опускаются.
- Что каждый вид сохраняет из защиты CanvasTTY (`keeps` в манифесте): worktree передаёт запуск без изменений
  (`launch`), поэтому там работает любой профиль, а слой изоляции CanvasTTY действует с worktree в роли проекта.
  Окна на сервере и в контейнере — нет (JSON-настройки, хуки и локальные мосты опускаются), поэтому CanvasTTY разрешает
  там только профиль normal, а окно сообщает, что хуки и базовая защита до агента не доходят; они объявляют `isolated`
  (слой изоляции этого компьютера не применяется), а контейнеры ещё и `confines` (одно монтирование проекта или его копии).
- Сбор изменений должен уложиться в 15 с, которые CanvasTTY даёт вызову инструмента или действию окна. Проверка в
  капсуле продолжается дольше; результат покажет значок окна, а журнал — *Show check result*.
- Агенту в контейнере нужен его CLI в образе и *Allow network*; на сервер ключи не передаются.
- Проверки в капсуле — только на этом компьютере (окна в worktree и локальных контейнерах); окно на сервере сначала
  заберите через Collect changes.
- Пока нет подготовки серверов, метрик, выбора сервера и запуска агентов только на выбранных файлах.
